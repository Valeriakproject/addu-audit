# Внешняя разведка Битрикс-сайта (без доступа)

Делается всегда, быстро, перед созвоном. Результат — список **внешне подтверждённых** проблем
и список **гипотез**, которые нельзя утверждать без админки.

## 1. Автоматический скан squirrelscan

```
squirrel audit <url>
```
Сохрани XML в `audits/{slug}-assets/`. Фиксируй: общий балл/grade, кол-во пройденных/предупреждений/проваленных.
Коммерчески понятные находки, которые он ловит: нет sitemap/robots, пустой title, нет H1, короткий description,
нет canonical, нет Open Graph, нет CSP/HSTS/защиты от clickjacking, формы без CAPTCHA, картинки без размеров (CLS),
тяжёлый CSS/страница, viewport запрещает масштабирование, элементы без доступного текста.

## 2. Признаки 1С-Битрикс
- HTTP-заголовок `X-Powered-CMS: Bitrix Site Manager`.
- Публичные ресурсы `/bitrix/js/`, `/bitrix/cache/`, `/bitrix/templates/{шаблон}/`.
- Готовый шаблон (напр. `dresscode`) — повод проверить обновления шаблона.
- Доступность `/bitrix/admin/` снаружи (отдаёт страницу авторизации).

## 3. HTTP-гигиена и дубли
- `http://site/` → должен быть 301 на `https://site/` (а не 200).
- Проверить дубли: `https://site/index.php`, `https://www.site/`, trailing slash — все не должны отдавать 200 без редиректа.
- Канонический домен + 301-редиректы с www/HTTP/`/index.php` + `rel=canonical` на шаблонах.

## 4. SEO-техника
- `robots.txt` — есть? (не 404, не HTML-заглушка Битрикса). Должен закрывать служебное и указывать Sitemap.
- `sitemap.xml` — есть? (не 404).
- `title` / `description` главной и ключевых шаблонов — заполнены, не шаблонные.
- `canonical` проставлен.

## 5. Безопасность (заголовки и cookie)
- Security headers: `Content-Security-Policy`, `Strict-Transport-Security` (HSTS), `X-Frame-Options`/анти-clickjacking,
  `X-Content-Type-Options`.
- Cookie flags: `Secure`, `HttpOnly`, `SameSite`.
- Формы с персональными данными — наличие CAPTCHA/антиспама.

## 6. Производительность и фронт
- Вес HTML и суммарный вес ресурсов (JS/CSS/images). Тяжёлая CSS-сборка, тяжёлая страница.
- Кэширование HTML для гостей (композит/кэш) — есть ли.
- Старый фронтенд-стек в шаблоне (устаревшие библиотеки).
- Картинки без указанных размеров (риск CLS), viewport без масштабирования.
- Core Web Vitals (LCP/CLS/INP) через Chrome DevTools MCP performance trace.

## 6.5. Мобильный рендер (обязательно, даже если сайт «вроде адаптивный»)

Проверять в браузере с эмуляцией мобильного на экране **390×844**, минимум на четырёх страницах
разных шаблонов: главная, внутренняя, список/новости, страница с таблицей.

Замерить и записать: наличие `meta viewport`, ширину макета (`documentElement.clientWidth`),
фактическую ширину содержимого (`body.scrollWidth`), величину горизонтальной прокрутки, масштаб,
число элементов, выходящих за экран, число кликабельных элементов ниже 44 px.
Готовый скрипт замера и правила подачи — в `qa-review-rules.md`, раздел 3.

⚠️ Масштаб считать от ширины макета (без `meta viewport` браузер берёт 980 px), а не от ширины
содержимого. 390/980 ≈ 0,40 — это верно; 390/1200 — завышение.

Снять два скриншота, 1280 px и 390 px, — в отчёт они идут парой. Без них раздел не сдаётся.

## 7. Что отдать в отчёт
Каждый пункт: **Проверка** (что и как смотрели) → **Риск** (почему это проблема для магазина/форм/SEO)
→ **Что предложить** (конкретное действие). Внешние факты помечать как подтверждённые, остальное — как гипотезы для админки.

**Каждый пункт этого чек-листа обязан попасть в отчёт** — в находки, если проблема подтвердилась,
или в раздел «что работает», если всё в порядке. Молчание про пункт клиент читает как «не проверяли».
Перед сдачей прогнать отчёт по `qa-review-rules.md`.
