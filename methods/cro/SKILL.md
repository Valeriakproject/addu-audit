# Multi-Page CRO Audit Skill

> Конверсионный аудит многостраничных сайтов с визуальным deliverable и деплоем на GitHub Pages.

## Когда использовать

Когда пользователь хочет провести маркетинговый/конверсионный аудит сайта, CRO-аудит, аудит посадочных страниц, или говорит: «сделай аудит сайта», «проверь конверсию», «что не так с сайтом», «как улучшить сайт», «аудит лендинга».

## Требования

- **Claude in Chrome** — для скриншотов страниц сайта
- **FTP на case.addu.ru** — публикация клиентского отчёта (см. `../assets/publish-case-addu.md`)
- Доступ к интернету для анализа сайта

## Воркфлоу

### Этап 0: Подготовка

1. Уточни у пользователя:
   - URL сайта для аудита
   - GitHub-репозиторий для деплоя (напр. `username/audits`)
   - Есть ли бриф от клиента (необязательно)

2. Создай рабочую директорию (единый корень для всех аудитов;
   `{domain}` — домен в ASCII с точками, напр. `18ga.ru`, `pazlypofoto.rf`):
```
audits/{domain}/cro/
├── index.html        # Итоговый отчёт
├── screens/          # Скриншоты страниц
│   ├── home.png
│   ├── page-1.png
│   └── ...
└── README.md
```

### Этап 1: Discovery (Разведка)

1. **Собери данные сайта** через `web_fetch`:
   - Главная страница
   - Все основные внутренние страницы (из навигации)
   - Страница «О компании» / «Контакты»

2. **ВАЖНО — провались до листовых страниц каталога.**
   Многие B2B-сайты построены как 3-уровневое дерево: Каталог → Категория-распутье → Конечный товарный листинг с таблицей и ценами. Если остановиться на 2-м уровне, увидишь «4 плитки и SEO-текст» и сделаешь ошибочный вывод «у них нет цен».

   **Алгоритм:**
   1. Фетчни первую категорию каталога.
   2. Задай в промпте WebFetch явный вопрос: **«Это конечный листинг товаров с таблицей и ценами, или промежуточная навигационная страница со ссылками на подкатегории? Если промежуточная — дай URL подкатегорий.»**
   3. Если страница промежуточная — фетчи 2-3 подкатегории из РАЗНЫХ веток (например: «тканая нерж. → общего назначения», «цветные металлы → латунь», «фильтровая»). Не одну — чтобы не получить смещённую выборку.
   4. На листовых страницах фиксируй: есть ли таблица товаров, какие колонки, цены в рублях / по запросу, фильтры, кнопка «в корзину» или «получить счёт».

3. **Проверь, что сайт реально продаёт «по запросу».**
   Если «цен нет» — попробуй:
   - Скачать прайс (часто доступен по email без регистрации).
   - Посмотреть карточку конкретного товара (3-4 уровень).
   - Проверить страницу «Как заказать» / «Оплата».
   Только после этого делай вывод «цены закрыты».

4. **Определи:**
   - Тип бизнеса, нишу, продуктовые направления
   - Ключевые факты для конверсии (опыт, цифры, гарантии, УТП)
   - Географию, ценовой сегмент
   - **Где живут цены и таблицы товаров** (на каком уровне иерархии)

5. **Проведи AJTBD-сегментацию** (Advanced Jobs To Be Done):
   - Выдели 3-5 сегментов ЦА
   - Для каждого: Job (задача), контекст решения, вопросы, возражения, критерии выбора, нужные артефакты

### Этап 2: Journey Mapping (Карта маршрутов)

1. **Определи продуктовые направления** (если несколько)
2. **Построй маршрут для каждого**:
   ```
   Поисковый запрос → Посадочная → Изучение → Решение → КОНВЕРСИЯ
   ```
3. Для каждого шага: вопросы посетителя, нужное действие, ключевые конверсии
4. **Определи типовые шаблоны страниц** для аудита

### Этап 3: Скриншоты

Используй **Claude in Chrome** для снятия скриншотов каждой аудируемой страницы:

```
1. tabs_context_mcp (createIfEmpty: true)
2. resize_window (1280 x 900)
3. Для каждой страницы:
   a. navigate → URL
   b. wait 3 сек (загрузка)
   c. computer screenshot (save_to_disk: true)
   d. Сохранить путь к файлу
```

**ВАЖНО:** При анализе страницы **проскролль её до конца**, делая скриншоты каждого значимого блока. Это нужно для шага «Функциональная идентификация блоков».

#### 3.1 ОБЯЗАТЕЛЬНО: интерактивная проверка воронки (не судить по статике!)

Скриншот и статичный HTML показывают только «состояние покоя». Целевое действие (форма,
бронь, корзина, заявка) почти всегда за **JS-взаимодействием** — модалка, попап, аккордеон,
кнопка-триггер. **Нельзя делать вывод «форма не работает / кнопка ведёт в никуда» по одному
только `href="#"` в разметке** — это классическая ложноположительная находка.

Перед выводами о воронке **прокликай каждый ключевой CTA** на каждом типе страницы:
1. Нажми «Забронировать / Купить / Оставить заявку / Заказать» и посмотри, что реально
   происходит: открылась ли модалка/попап, появилась ли форма, куда ведёт кнопка.
2. `href="#"`, `href="#anchor"`, `data-popup`, классы `popup-control`, `mfp-hide`,
   `modal`, `fancybox`, `magnific` — это **триггеры JS-модалок**, а не битые ссылки.
   Прежде чем писать «пустой якорь», проверь, есть ли на странице элемент с этим `id`
   (скрытая модалка) и открывается ли он по клику.
3. Открой форму и перечисли её **реальные поля** (после раскрытия модалки), а не те, что
   видны в свёрнутом состоянии. Отметь механизм отправки (`ajax_form`, `action=...`).
4. НЕ отправляй реальную заявку/бронь (не создавай ложный лид) — проверяется открытие и
   состав формы, а факт доставки помечается как «проверить с доступом».

Инструменты: Claude in Chrome (`computer` click / `find`) или chrome-devtools MCP
(`click`, `take_snapshot`, `evaluate_script` для проверки `document.querySelector('#id')`).

### Этап 4: Аудит по шаблонам

**Перед началом — выбери ПРАВИЛЬНЫЕ страницы для аудита.**
Для каждого типа шаблона бери самую глубокую (листовую) страницу, где живёт реальная конверсия, а НЕ обзорную. Например:
- Для «Категория» — НЕ страницу-распутье, а конечный товарный листинг с таблицей.
- Для «Карточка товара» — реальную карточку с ценой и кнопкой заказа.
- Для «Каталог» — корневую страницу каталога (там распутья допустимы).

Если страница оказалась распутьем — аудитируй её отдельно как тип «Категория-распутье», а параллельно — листовую как «Категория-листинг». Это два разных шаблона с разными критериями.

**Для каждого типа страницы:**

#### 4.1 Функциональная идентификация блоков

Определи, что каждый блок на странице ДЕЛАЕТ для посетителя, а не как он называется:
- «Наши цены» с фото работ = **PORTFOLIO + PRICING** (не просто «прайс»)
- «Материалы» = может быть **обучающий контент** (если полезно для выбора) или **технический шум** (если клиент не в теме)
- «О нас» = **TRUST** (если содержит факты и доказательства)

Используй библиотеку компонентов (см. references/component-library.md):
HERO, PROOF, PORTFOLIO, TRUST, QUIZ, FAQ, NEXT_STEP, CROSS_SELL, IDENTIFY, PRICING, PROCESS

#### 4.2 «Как сейчас» — текущая структура блоков
#### 4.3 «Почему может не конвертить» — проблемы с маркировкой серьёзности:
  - **КРИТ** (c) — убивает конверсию прямо сейчас
  - **ВЫСОК** (h) — сильно влияет на решение
  - **СРЕДН** (m) — снижает доверие
  - **ПРОВЕРИТЬ** (r) — гипотеза, не подтверждённая интерактивно/на одинаковых сущностях

**Правило достоверности (обязательно).** Находки формата «форма не работает / кнопка ведёт
в никуда / бронь оборвана / цена расходится / телефоны противоречат» — **техничны и
фальсифицируемы**, поэтому их НЕЛЬЗЯ ставить как КРИТ без прямой проверки:
  - «Сломано/ведёт в никуда» → допустимо только после интерактивной проверки (см. п. 3.1).
    Если триггер открывает модалку с рабочей формой — это НЕ поломка. Не проверил кликом →
    ставь **ПРОВЕРИТЬ (r)**, а не КРИТ.
  - «Цены/телефоны противоречат» → сравнивай **одинаковые сущности** (тот же номер/тот же
    отель на разных страницах). Разные цены у разных классов номеров или разные телефоны у
    разных локаций сети — это норма, а не противоречие. Внутренняя согласованность (напр.
    750 ₽/час × 2 = 1500 ₽) не считается ошибкой. Не свёл на одинаковых сущностях → **ПРОВЕРИТЬ (r)**.
  - Перед сдачей отчёта перечитай все КРИТ-находки и убедись, что каждая проверена по факту,
    а не выведена из разметки. Ложноположительная критичная находка в клиентском отчёте
    дороже пропущенной — она подрывает доверие ко всему аудиту.

#### 4.4 «Новая структура» — идеальная последовательность блоков с:
  - Тегами компонентов из библиотеки
  - Конкретными текстами H1, подзаголовков, CTA
  - Полями форм под конкретный интент

### Этап 5: Узкие горлышки

Агрегируй проблемы по всем шаблонам. Приоритизируй. Для каждой проблемы напиши **конкретное решение**.

### Этап 6: ТЗ на улучшения

Раздели на:
- **Быстрые правки** (1-3 дня) — с оценкой эффекта
- **Структурные изменения** (1-2 недели) — с оценкой эффекта
- **Контент-задачи** (участие клиента) — что нужно сфотографировать/снять/написать

### Этап 7: Генерация отчёта

**Единый дизайн обязателен.** Все аудиты выводятся в тёплом светлом стиле addu.ru
(янтарный акцент, hero + сводка-карточки, бейджи серьёзности, блок «Контакт по проекту») —
сначала прочитай `../assets/design-system.md` и следуй ему. Эталон вида — пакет аудитов
152-ФЗ (`addu-152fz-toolkit`).

1. Скопируй болванку `../assets/base-template.html` в `audits/{domain}/cro/index.html`
   (палитра, логотип addu.ru, hero, сводка, бейджи, контакт и каркас вкладок уже встроены).
2. Заполни плейсхолдеры hero/сводки и опиши данные аудита JS-массивами (`pages`, `bottlenecks`,
   `compLib`), напиши render-функции. Вкладки: Обзор / Аудит страниц / Узкие горлышки /
   ТЗ на улучшения / Компоненты.
3. Встрой скриншоты как base64:
```javascript
// Конвертация скриншота в base64 для встраивания
const fs = require('fs');
const img = fs.readFileSync('screens/home.png');
const base64 = img.toString('base64');
// Вставить в HTML как: src="data:image/png;base64,${base64}"
```

Если base64 делает файл слишком большим (>5MB), используй внешний сервис:
```
src="https://image.thum.io/get/width/1200/crop/700/https://site.ru/"
```

### Этап 8: Публикация на case.addu.ru (ОБЯЗАТЕЛЬНО)

Клиентскую версию маркетингового аудита ВСЕГДА публикуем на нашем ресурсе
**https://case.addu.ru/** и отправляем клиенту ссылку, а не файл.

Полная процедура и доступы — в `../assets/publish-case-addu.md`.
**Пароль не запрашивать** — реквизиты FTP лежат локально (см. тот файл).

Кратко: загрузи `index.html` (и папку `screens/`, если скриншоты не встроены в base64)
по FTP в папку `{domain}` → клиентская ссылка `https://case.addu.ru/{domain}/`.
Проверь, что ссылка открывается, прежде чем отдавать клиенту.

### Этап 9: Отправка клиенту

Сформируй ссылку и сообщение:
```
Ссылка на аудит: https://case.addu.ru/{domain}/

Привет! Подготовили CRO-аудит вашего сайта — вот интерактивный отчёт.
Внутри: анализ {N} страниц, {M} рекомендаций, конкретные тексты и структуры.
```

## Советы

- **Скриншоты первого экрана** достаточно для deliverable. Если нужен полный скролл — делай несколько скриншотов и собирай коллаж.
- **Шаблон отчёта** — самостоятельный HTML без зависимостей. Работает офлайн (кроме шрифтов Google Fonts и скриншотов thum.io).
- **Для клиента** важнее всего: карта маршрутов, вайрфреймы «до/после», конкретные тексты CTA, и визуальные скриншоты.
- **Время на один аудит**: 15-30 минут (Discovery + анализ + генерация отчёта).
