# Интерактивная процедура (chrome-devtools MCP)

Закрывает пробел SquirrelScan: реальные клики, открытие модалок, проверка форм без отправки, JS-ошибки, упавшие запросы, мобильный рендер. Все шаги — через MCP `chrome-devtools` (инструменты `mcp__chrome-devtools__*`). Если они отложены — подгрузить через ToolSearch (`select:mcp__chrome-devtools__navigate_page,...`).

## Принципы
- Работаем по реальному рендеру в Chrome (важно для HTTP/windows-1251 сайтов).
- **Формы НЕ отправляем.** Проверяем обвязку, но финальный сабмит не жмём.
- Каждый дефект фиксируем доказательством: скриншот, текст ошибки консоли, URL упавшего запроса.

## Шаги

### 1. Открыть сайт и снять базовое состояние
- `navigate_page` → URL сайта.
- `list_console_messages` → сохранить ошибки/предупреждения при загрузке.
- `list_network_requests` → отметить запросы со статусом ≥400, `failed`, `blocked`, mixed-content (http-ресурсы).
- `take_snapshot` → получить дерево интерактивных элементов (кнопки, ссылки, формы, триггеры модалок).
- `take_screenshot` (desktop) → первый экран главной.

### 2. Перечислить и проверить кнопки/ссылки
- Из snapshot собрать список кликабельных элементов: пункты меню, CTA («Сделать», «Каталог», «Заказать»), кнопки-триггеры модалок, кнопки слайдера/табов.
- Для каждого ключевого элемента: `click` → наблюдать результат (навигация / открытие модалки / действие).
  - после клика: `list_console_messages` (новые ошибки?), при навигации — статус страницы.
- Помечать «мёртвые» кнопки: `href="#"`/`javascript:void`, обработчик падает или ничего не происходит.
- Не обязательно кликать каждую из сотен товарных ссылок — берём представителей каждого типа (меню, CTA, карточка товара, футер, соцсети) + всё, что squirrel пометил битым.

### 3. Модальные окна
- Найти триггеры (напр. «Заказать обратный звонок», `callback_modal_open()`), кликнуть, убедиться, что модалка открывается; закрыть, убедиться, что закрывается.
- Снять `take_screenshot` открытой модалки.

### 4. Формы (без отправки)
Для каждой формы (callback-модалка, оформление заказа, поиск, вход):
- проверить наличие и редактируемость полей (заполнить тестовым значением через `fill`/`fill_form`, но **не сабмитить**);
- проверить клиентскую валидацию: пустой required, кривой телефон/email — должна ругаться;
- отметить наличие защиты (reCAPTCHA/капча), если ожидается;
- проверить доступность `action`-эндпоинта отдельным HEAD/GET-запросом (через Bash `curl -I`), **не отправляя данные формы**;
- снять console при взаимодействии (ошибки JS в обработчике формы).

### 5. Скорость и доступность
- `performance_start_trace` / `performance_stop_trace` или `lighthouse_audit` по главной (и 1–2 ключевым страницам) → Performance, Accessibility, Best Practices, SEO + LCP/CLS/INP/TBT.
- Зафиксировать значения в находки.

### 6. Мобильная версия
- `emulate` или `resize_page` под мобильный (например 390×844).
- `navigate_page` (или перезагрузка), `take_screenshot` → проверить: нет горизонтального скролла, контент не уезжает, меню/кнопки доступны, tap-targets не слипаются.
- Снять console/network на мобильном профиле.

### 7. Сохранить артефакты
В `documents/{slug}-techaudit/raw/`:
- `screenshot-desktop-*.png`, `screenshot-mobile-*.png`, `screenshot-modal-*.png`;
- `console.md` — собранные ошибки/предупреждения консоли;
- `network-failures.md` — список упавших/проблемных запросов;
- `lighthouse.md`/json — результаты Lighthouse.

## На что особенно смотреть (типичные тех-проблемы)
- jQuery/скрипты, подгружаемые по `http://` (mixed-content при HTTPS).
- 404 на картинки/ассеты.
- Кнопки, чьи обработчики висят на устаревших библиотеках.
- Формы, чей `action` отдаёт 404/5xx.
- Mojibake из-за неверной отдачи charset.
- Долгий LCP из-за тяжёлых несжатых картинок.
- Сломанная мобильная вёрстка на старых табличных макетах.
