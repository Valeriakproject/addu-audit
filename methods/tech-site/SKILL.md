# Addu — Технический аудит сайта (`site-tech-audit`)

Инструмент технической проверки работоспособности одного сайта. Не путать с `addu-152fz-audit` (юр-комплаенс по персональным данным) и CRO-аудитом (конверсия). Этот скилл отвечает на вопрос «всё ли на сайте технически работает».

База скилла: `Tools/site-tech-audit/`. Все референсы — рядом в `references/`, шаблон отчёта — в `assets/`.

## Когда использовать
- Клиент жалуется, что «сайт глючит / что-то не работает».
- Нужно показать владельцу конкретные технические дефекты и смету на починку.
- Перед/после доработок — зафиксировать состояние.

Не использовать, если нужен аудит по 152-ФЗ (тогда `addu-152fz-audit`) или маркетинговый аудит (CRO).

## Движок (гибрид)
- **SquirrelScan** (CLI, статический краулер, 230+ правил) — ссылки, редиректы, mixed-content, SEO, картинки, доступность, crawl, charset, скорость (оценка). Установка и команды — `references/squirrelscan-guide.md`.
- **chrome-devtools MCP** (реальный Chrome) — интерактив, которого нет у SquirrelScan: клики по кнопкам, открытие модалок, обвязка форм (без отправки), JS-ошибки консоли, упавшие сетевые запросы, Lighthouse, мобильный рендер. Процедура — `references/interactive-procedure.md`.

Полная карта «что чем проверяем» и маппинг severity — `references/check-catalog.md`.

## Вход
- **URL сайта** (обязательно). Нормализовать.
- **Slug** (опционально). Если не задан — вывести из домена: `www.example.ru` → `example-ru`. Slug определяет имя папки вывода.

## Что делает (workflow)

1. **Подготовка.** Нормализовать URL, вычислить slug, создать `documents/{slug}-techaudit/raw/`. Убедиться, что SquirrelScan установлен (`squirrel --version`); если нет — поставить по `references/squirrelscan-guide.md` (при недоступности — `npx`, либо пропустить squirrel-часть и честно отразить сокращённое покрытие).

2. **SquirrelScan-скан.** Запустить (coverage по размеру сайта — quick/surface/full; для HTTP-сайтов добавить `--http`, всегда `--offline -y`):
   ```bash
   squirrel audit <URL> -C quick --offline --http -y -f json -o documents/{slug}-techaudit/raw/squirrel.json
   squirrel audit <URL> -C quick --offline --http -y -f html -o documents/{slug}-techaudit/raw/squirrel.html
   ```
   Распарсить `score.overall`/`grade`, категории, `issues[]` (severity error/warning) — выбрать значимые.

3. **Интерактивный проход (chrome-devtools MCP)** по `references/interactive-procedure.md`:
   - открыть сайт, снять console (errors/warn) и network (статус ≥400, failed, mixed-content);
   - snapshot → перечислить кнопки/ссылки/формы/модалки; кликать ключевые элементы, после каждого — снова console;
   - модалки: открыть/закрыть, скриншот;
   - формы: проверить поля, валидацию, защиту, доступность action-эндпоинта (HEAD через Bash) — **без сабмита**;
   - Lighthouse/трейс по главной (+1–2 страницам);
   - мобильный профиль (`resize_page`/`emulate`) + скриншоты desktop и mobile;
   - сохранить артефакты в `raw/` (скриншоты, заметки console/network).

4. **Слияние и приоритизация.** Объединить находки squirrel + интерактива, дедуп, проставить severity (`hard_fail`/`risk_flag`/`manual_review`/`ok`). Особое внимание — тому, что ломает пользователю работу (мёртвые кнопки, сломанный конструктор/формы, JS-ошибки, нет HTTPS, сломанный мобильный).

5. **Смета.** Посчитать починку по `references/estimate-rules.md` (2500 ₽/ч), одна фиксированная цена.

6. **Выход.** Сгенерировать три файла (см. ниже) + сырьё в `raw/`.

7. **Резюме в чат** (3–5 строк): статус, health-score, объём работ, путь к отчёту, что отправить клиенту.

## Выход

Папка `documents/{slug}-techaudit/`:

### 1. `audit-tech-{slug}.html`
Клиентский HTML-отчёт по `assets/report-template.html` и `references/report-structure.md`. Светлый стиль, готов к PDF. Логотип Addu по прямой ссылке `https://addu.ru/assets/templates/addu/img/logo.webp`. Содержит: обложку, «Почему это важно», 3 summary-карточки (статус / что значит / объём, без цены), «Что проверили», карточки находок по зонам, план работ + фиксированную цену, CTA, контакты (Иван Меньшов, +7 (495) 150-32-00, sales@addu.ru), дисклеймер из `references/scope-disclaimer.md`.

НЕ включать в HTML: внутренние severity-коды, сырые англоязычные строки squirrel, письмо менеджеру, технический жаргон уровня кода.

### 2. `tech-findings.md` (внутренний, машиночитаемый)
Строго по `references/findings-template.md`: шапка (платформа, health-score, чем проверяли), `## Сводка` (таблица severity), `## Проверенные страницы`, `## Обнаруженные формы`, `## Технические находки` (каждая с полями Зона/Где/Что/Severity/Почему/Рекомендация/Чем выявлено), `## Оценка работ`, `## За пределами технического объёма`.

### 3. `manager-email.md`
Короткое письмо для пересылки клиенту вместе с PDF. Не попадает в HTML.

Плюс `raw/`: `squirrel.json`/`squirrel.html`, скриншоты (desktop/mobile/модалки), заметки console/network.

## Границы
- Это техническая проверка, **не пентест и не нагрузочное тестирование**, не гарантия.
- **Формы не отправляем** — проверяем обвязку, фактическую доставку помечаем `manual_review`.
- Если сайт недоступен — честно указать, не выдумывать находки.
- Не зашивать платформу: если Bitrix — давать Bitrix-специфику (шаблоны, компоненты, веб-формы); Tilda/WordPress/самопис — соответственно; если неизвестна — платформо-нейтрально.
- Severity ставить по факту наблюдения, не по предположению.
- Не продавать здесь support-контракт — это разовый пакет технических правок.
