# Addu 152-ФЗ — Выпуск пакета документов и ТЗ

Финальный шаг конвейера. На входе — три файла, на выходе — готовый рабочий пакет: политика, согласие, разметка чекбоксов, cookie-баннер, план для разработчика, QA-чек-лист, completion note.

## Когда использовать

- Skill `addu-152fz-intake` уже создал `intake-context.md`.
- Клиент прислал ответы на анкету; они сохранены в `documents/{slug}-152fz/answers.md` в любой форме (можно вставить целиком текст письма клиента).
- Менеджер хочет получить готовые документы и ТЗ для разработчика.

Не использовать:
- если `answers.md` не существует — попросить менеджера сохранить ответы клиента;
- если на конкретные вопросы клиент ответил «не знаю» / «потом» по `required`-ключам — останавливаться и поднимать менеджеру.

## Вход

- **Slug клиента** (обязательно). Skill ищет файлы в `documents/{slug}-152fz/`:
  - `audit-findings.md` — обязателен;
  - `intake-context.md` — обязателен;
  - `answers.md` — обязателен.

## Что делает

### Шаг 1. Парсинг ответов клиента

Читает `answers.md` (это свободный текст от клиента, может быть письмо целиком). Извлекает значения для ключей, перечисленных в `intake-context.md`:

- `operator_full_name`, `operator_inn`, `operator_ogrn` и т.д.

Парсинг — это работа модели, не regex. Применять здравый смысл:
- если в тексте есть «ИНН 7712345678» — это `operator_inn`;
- если есть «у нас Yandex 360» — это `email_service`;
- если есть «рассылок не делаем» — `has_marketing_rasslyka: no`;
- если есть «Метрика не используется» — `yandex_metrika_counter: none`.

Если что-то спорное — задать менеджеру один уточняющий вопрос через `AskUserQuestion` (например, «В ответе клиента упомянуты "СДЭК и наш курьер" — записать обе службы доставки?»). Не больше 2-3 уточнений за прогон.

### Шаг 2. Валидация

Проверить, что все `required`-ключи из `intake-context.md` имеют значение в распарсенном виде.

Если **хотя бы одного** required-ключа нет:
- НЕ генерировать документы;
- создать файл `documents/{slug}-152fz/missing-answers.md` со списком: «не хватает: ИНН, ОГРН, хостинг» с подсказкой менеджеру, как сформулировать дозапрос клиенту;
- вернуть в чат сообщение «Не хватает данных: {список}. См. missing-answers.md. После получения — пополни answers.md и запусти меня снова».
- остановиться.

### Шаг 3. Подбор шаблонов

Если валидация прошла, открыть шаблоны из `templates/`:
- `policy-template.md`
- `consent-template.md`
- `form-checkboxes-template.md`
- `cookie-banner-template.md`
- `action-plan-template.md`
- `qa-checklist-template.md`
- `completion-note-template.md`
- `notes-and-sources-template.md`

Шаблоны содержат блоки с плейсхолдерами `{{KEY}}` и условные секции вида `{{#if has_cart}}...{{/if}}`. Условные секции включаются на основе findings + answers (есть ли корзина, есть ли регистрация, какая CMS и т.д.).

### Шаг 4. CMS-специфика

CMS определяется из `intake-context.md` (поле «CMS»). Применить CMS-специфичные блоки:

- **Bitrix:** ТЗ ссылается на админку Bitrix (Сервисы → Веб-формы), события `OnBeforeUserRegister`, `OnBeforeSubscriptionAdd`, шаблоны `/bitrix/templates/*/`. Cookie-баннер вставляется в `footer.php`. Редирект через `.htaccess` или `OnBeforeProlog`.
- **Tilda:** ТЗ ссылается на «Настройки страницы → Дополнительный код», поле Checkbox в форме, T972 для cookie. Доступ через «Сотрудничество», не через пароль.
- **WordPress:** ТЗ ссылается на админку WP, плагины Contact Form 7 / WPForms, Cookie Notice / Complianz, `wp_redirect()`. Доступ через роль Administrator или плагин-менеджер.
- **Иное / неизвестно:** ТЗ остаётся платформо-нейтральным; в начале файла action-plan добавлять пометку «CMS не определена — разработчик клиента уточнит детали реализации под свою платформу».

См. `references/cms-fragments.md` — там CMS-блоки текста, которые подставляются по платформе.

### Шаг 5. Генерация

Сгенерировать в `documents/{slug}-152fz/`:

1. `policy.md` — текст «Политики обработки персональных данных»;
2. `personal-data-consent.md` — текст «Согласия на обработку персональных данных»;
3. `form-checkboxes.md` — разметка чекбоксов для каждой найденной формы;
4. `cookie-banner.md` — текст и разметка cookie-баннера;
5. `action-plan.md` — план для разработчика, последовательность работ;
6. `qa-checklist.md` — приёмочный чек-лист;
7. `completion-note.md` — шаблон финального письма клиенту после внедрения;
8. `notes-and-sources.md` — внутренние пометки и допущения.

Все плейсхолдеры должны быть заполнены — никаких `{{...}}` в выходных файлах.

### Шаг 6. Финальная проверка перед сдачей

Перед тем как объявить пакет готовым, прогнать самопроверку:

- [ ] нет `{{` в выходных файлах (grep по папке);
- [ ] во всех документах указаны реальные ИНН, ОГРН, адрес из `answers.md`;
- [ ] CMS-специфичные ссылки соответствуют CMS клиента (нет упоминаний Tilda для Bitrix-клиента и наоборот);
- [ ] список обработчиков в политике и согласии одинаков и соответствует ответам клиента;
- [ ] в action-plan указаны конкретные имена полей форм из findings (`personalInfo`, `personalInfoFastBuy` и т.д. для Bitrix);
- [ ] если у клиента нет рассылок — не добавлять отдельный чекбокс на рекламу в подписке (но чекбокс согласия на ПДн всё равно обязателен).

Если самопроверка не прошла — поправить и повторить.

### Шаг 7. Сообщение в чат

После генерации:
- короткая сводка (5-7 строк): сколько файлов создано, какая CMS, ключевые правки;
- путь к `action-plan.md` (главный документ для разработчика);
- что делать менеджеру дальше: согласовать тексты с клиентом, передать `action-plan.md` разработчику, по готовности — прогнать `qa-checklist.md`.

## Поведение в краевых случаях

**Клиент ответил противоречиво:**
- «у нас нет CRM» в одном предложении и «заявки из амо в Telegram» в другом → задать уточнение менеджеру, не угадывать.

**Клиент ответил «не знаю» по required-ключу:**
- остановить генерацию;
- в `missing-answers.md` написать конкретно: «клиент не знает ИНН — попроси найти в выписке ЕГРЮЛ на nalog.ru по названию компании»;
- не выдумывать.

**На сайте нашлась форма, про которую в анкете не спросили:**
- не блокировать;
- сгенерировать чекбокс по дефолтной разметке;
- добавить в `notes-and-sources.md` пометку: «форма X найдена аудитом, в анкете не уточнялась — действия по умолчанию».

**Клиент попросил не упоминать обработчика (например, «хостинг не пишите»):**
- учесть, не упоминать;
- добавить в `notes-and-sources.md` пометку, что клиент просил скрыть, и предупреждение, что это снижает полноту политики.
