# Аудиты ADDU

Рабочий набор агентства ADDU для аудитов сайтов. Читай этот файл перед любой задачей и следуй ему.

**Этот файл главнее всего остального в репозитории.** Методики в `methods/` — источник предметных
знаний, но если они противоречат правилам отсюда или из `rules-addu.md`, действуют наши правила.
Всё, что присылали раньше отдельными файлами или писали в чате, считается устаревшим.

## Два режима, не путать

**Пресейл — по умолчанию.** Работа по холодному контакту, до продажи, когда с компанией никто не
разговаривал. Спросить у клиента нечего и не у кого.

- **Не задавай вопросов про бизнес компании.** Выручка, средний чек, аудитория, бюджеты, каналы,
  список конкурентов, приоритетные запросы — ответов нет и взять их негде.
- Работай только с открытыми источниками: сайт и его разметка, подключаемые файлы, публичные
  реестры, поисковая выдача, отзывы на картах и отзовиках.
- Чего снаружи не видно — не выдумывай. Помечай «требует уточнения у клиента» и собирай отдельным
  списком в конце отчёта. Это нормальная часть пресейл-аудита и повод для созвона.
- **Не отменяй и не приостанавливай работу из-за нехватки вводных.** Сделай по доступному и отдай
  результат. Единственная причина остановиться — сайт физически не открывается.

**Клиент уже платит.** Полное маркетинговое исследование, внедрение, документы по 152-ФЗ после
оплаты. Здесь вводные собираются у клиента как положено, вопросы задавать нужно, правила пресейла
не применяются.

Не понимаешь, какой режим — спроси одним вопросом: «это пресейл или клиент уже оплатил?»

## Какую методику брать

**Пресейл, до продажи:**

| Запрос | Файл |
|---|---|
| 152-ФЗ, персональные данные, политика, cookie, согласия | `methods/152fz/audit-152fz.md` |
| Маркетинговое исследование по холодному контакту: рынок, конкуренты, сегменты роста | `methods/market-research-cold.md` |
| Технический аудит любого сайта (сканер + браузер) | `methods/tech-site/SKILL.md` |
| Технический аудит именно на 1С-Битрикс | `methods/tech/SKILL.md` |
| Конверсия многостраничного сайта | `methods/cro/SKILL.md` |
| Конверсия интернет-магазина | `methods/estore/SKILL.md` |
| Конверсия лендинга | `methods/landing/SKILL.md` |
| SEO-аудит | `methods/seo/SKILL.md` |
| ИИ-аудит, видимость в нейросетях, AI SEO | `methods/ai-seo/SKILL.md` |

**После оплаты, работа с клиентом:**

| Шаг | Файл |
|---|---|
| Полное маркетинговое исследование (бриф из 11 полей) | `methods/market-research/SKILL.md` |
| 152-ФЗ, шаг 2: анкета клиенту | `methods/152fz-intake/SKILL.md` |
| 152-ФЗ, шаг 3: документы и ТЗ разработчику | `methods/152fz-generate/SKILL.md` |
| 152-ФЗ, шаг 4: инструкция по уведомлению РКН | `methods/152fz-rkn/SKILL.md` |

Конвейер 152-ФЗ идёт строго по порядку: аудит до продажи, затем анкета после оплаты, затем
генерация документов по ответам клиента, затем инструкция по РКН. Перепрыгивать шаги нельзя,
каждый следующий читает результат предыдущего.

Узкие SEO-задачи (магазины приложений, программатик, микроразметка, архитектура сайта) —
в `methods/seo-extra/`.

Если клиент холодный, бери пресейл-версию, а не полное исследование с брифом.

## Правила, общие для всех аудитов

1. **Находка без доказательства не пишется.** Сначала открой источник, потом утверждай. Не
   проверил — «требует ручной проверки», и в смету это не идёт.
2. **Ничего не выдумывать:** ни конкурентов, ни исследования, ни цифры, ни отзывы, ни трафик.
   Каждая внешняя цифра идёт со ссылкой и периодом либо с пометкой `(оценочно)` и расчётом.
3. **Оформление берётся из шаблона,** а не придумывается: `assets/report-template.html`,
   принципы — `assets/design-system.md`. Тарифы только из `assets/tariffs.md`, не выдумывать.
4. **Смета** по ставке 2 500 ₽/час, часы округлять вверх до 0,5 ч. Клиенту одна фиксированная
   сумма, без диапазона. Проверить, что часы на обложке, «Итого» в таблице и итог совпадают.
5. **Не писать** «сайт незаконен», «компания нарушает закон», «гарантируем отсутствие претензий».
6. Если аудит занял меньше получаса, почти наверняка часть источников не открыта. Вернуться.
7. **Перед сдачей сверься с примером.** В `examples/` лежат готовые аудиты-эталоны, там видно
   ожидаемую структуру, глубину находок и оформление. Если твой отчёт заметно беднее — вернись и
   доработай. Копировать текст оттуда нельзя, ориентироваться на уровень нужно.

## Что отдаём клиенту

- **152-ФЗ и технический** — PDF. Не HTML и не ссылка.
- **Маркетинговые (исследование, CRO, магазин, лендинг)** — публикуем на case.addu.ru и даём ссылку.
  **Каждый тип в свою подпапку**, иначе новая работа затрёт предыдущую:
  исследование в `{домен}/research/`, аудит конверсии в `{домен}/cro/`, SEO в `{домен}/seo/`,
  ИИ-аудит в `{домен}/ai-seo/`. В корень `{домен}/` не публиковать. Порядок в `rules-addu.md`.
- **SEO и ИИ-аудит** — по договорённости, обычно в составе пакета.

Скидка 30% — только на 152-ФЗ, подробности в `rules-addu.md`.

Письма клиенту — `letters.md`.

## Куда сохранять результат

Всё по клиенту складывать в `audits/{домен}/` внутри этой папки:

```
audits/example.ru/
├── research/
│   ├── index.html      # клиентский отчёт
│   └── findings.md     # внутреннее, клиенту не показывать
├── cro/
│   └── index.html
└── 152fz/
    ├── index.html
    ├── findings.md
    └── letter.md
```

Подпапка называется по типу работы и совпадает с адресом публикации. Так по одному домену можно
сделать несколько разных работ, и они не будут затирать друг друга.

Домен латиницей, точки оставлять (`example.ru`), для `.рф` использовать `-rf`.
Папка `audits/` в репозиторий не попадает, там данные клиентов.

## Если ты читаешь этот файл по ссылке

Значит, репозиторий не подключён, а правила тебе дали по прямому адресу. Тогда `git pull` делать не
нужно, а все упомянутые ниже файлы открывай по тому же базовому адресу, меняя только конец пути:

```
https://raw.githubusercontent.com/Valeriakproject/addu-audit/main/<путь к файлу>
```

Например `methods/152fz/audit-152fz.md` открывается как
`https://raw.githubusercontent.com/Valeriakproject/addu-audit/main/methods/152fz/audit-152fz.md`.

Открывай нужные файлы по мере работы: методику под задачу, шаблон отчёта, правила выдачи.
Не пересказывай их пользователю, просто следуй.

## Первое действие в каждой новой сессии

Молча, без вопросов и без напоминаний, выполни в этой папке:

```
git pull
```

Это займёт секунду и подтянет свежие правила. Пользователю про это ничего писать не нужно, он не
должен знать про git. Если обновление не прошло, не останавливайся: работай по тем правилам, что
есть, но в конце ответа одной строкой скажи, что правила могли устареть.

После обновления сразу берись за задачу. Не задавай уточняющих вопросов про то, какой это тип
аудита, если из запроса понятно, — сверься с таблицей выбора методики выше.

## Пользователь не технический

Менеджер по продажам не знает, что такое git, репозиторий, командная строка и папки проекта.

- Не проси его выполнять команды, открывать терминал, что-то устанавливать или настраивать.
- Не объясняй ему технические детали, если он не спросил.
- Всё техническое делай сам.
- Если что-то реально не можешь сделать сам, напиши одной понятной фразой, что передать Лере.
  Без стектрейсов и без предложений «выполните такую-то команду».
