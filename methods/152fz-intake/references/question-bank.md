# Банк вопросов для анкеты

Каждый вопрос помечен ключом (используется в `intake-context.md` и в `answers.md`), формулировкой и категорией (обязательный / условный / опциональный).

## Категории обязательности

- `required` — без ответа `generate` остановится. Только базовые юр.реквизиты и контакт.
- `expected` — нужен для качественной генерации, но при отсутствии generate подставит «не указано» или общую формулировку.
- `optional` — задаём только если условия адаптации совпали.

## Группа 1. Реквизиты оператора (всегда обязательная)

Заголовок группы: «Реквизиты компании»
Контекст: «Эти данные попадут в политику, согласие и юр.блок в footer сайта.»

- key: `operator_legal_form`, required, «Кто является оператором ПДн: ООО / АО / ИП / самозанятый / физлицо?»
- key: `operator_full_name`, required, «Полное наименование оператора (как в ЕГРЮЛ/ЕГРИП)»
- key: `operator_inn`, required, «ИНН»
- key: `operator_ogrn`, required, «ОГРН (для юр.лиц) или ОГРНИП (для ИП)»
- key: `operator_legal_address`, required, «Юридический адрес»
- key: `operator_mail_address`, expected, «Почтовый адрес для обращений по ПДн — если отличается от юридического»
- key: `operator_pd_email`, required, «Email для обращений по вопросам ПДн (если на сайте виден контактный email — можно его подтвердить или указать отдельный)»
- key: `operator_pd_phone`, optional, «Телефон для обращений по ПДн — если хотите указать»

## Группа 2. Хранение данных и обработчики (большая часть — expected)

Заголовок группы: «Где хранятся заявки и заказы»
Контекст: «Эти сервисы перечисляются в политике как третьи лица, через которых проходят данные.»

- key: `hosting_provider`, required, «Хостинг-провайдер сайта (REG.RU / TimeWeb / Beget / собственный сервер / иное)»
- key: `where_leads_go`, expected, «Куда уходят заявки с форм (email / CRM / Telegram / Google Sheets / иное)»
- key: `email_service`, expected, «Сервис корпоративной почты (Yandex 360 / Mail.ru для бизнеса / Google Workspace / иное)»
- key: `crm`, expected (если where_leads_go упомянул CRM), «Какая CRM-система (Битрикс24 / amoCRM / Мегаплан / 1С / иное)»
- key: `telephony`, optional, «IP-телефония — используется ли, какой провайдер? Записываются ли звонки?»

## Группа 3. Корзина и заказы (условная — только если в findings есть корзина)

Заголовок группы: «Оплата и доставка»

## Группа 4. Аналитика и виджеты (условная — формулировка зависит от findings)

Заголовок группы: «Аналитика и сторонние сервисы»
Контекст: «Мы перечисляем их в политике и cookie-баннере.»

Формулировка зависит от того, что нашёл аудит:

- key: `yandex_metrika_counter`, expected:
  - если в findings есть Метрика с ID: «Подтвердите номер счётчика Яндекс.Метрики: {ID}»
  - если Метрики нет: «Подключаете ли Яндекс.Метрику динамически (GTM, модуль CMS) или планируете подключить?»
- key: `gtm_container`, optional (если в findings нет видимых счётчиков), «Используете ли Google Tag Manager? Если да — ID контейнера»
- key: `chat_widget`, optional (если в findings есть чат или callback-виджет), «Какой чат / callback используется (JivoSite, Carrot Quest, Verbox, Talk-Me, иное)?»
- key: `calltracking`, optional, «Коллтрекинг (Calltouch / Roistat / CoMagic) — используется?»
- key: `pixels`, optional, «Рекламные пиксели VK / myTarget / иное?»

## Группа 5. Рекламные коммуникации (всегда нужна)

Заголовок группы: «Рассылки и рекламные сообщения»
Контекст: «От этого зависит, нужны ли отдельные согласия на рекламу в формах.»

- key: `has_marketing_rasslyka`, required, «Отправляете ли клиентам рекламные сообщения (email-рассылки, SMS, сообщения в мессенджерах)?»
- key: `marketing_channels`, expected (если has_marketing_rasslyka=yes), «По каким каналам (email / SMS / Telegram / WhatsApp / VK / иное)»
- key: `newsletter_service`, expected (если has_marketing_rasslyka=yes), «Сервис рассылок (Unisender / Sendsay / Mailchimp / DashaMail / иное)»
- key: `plans_marketing`, optional (если has_marketing_rasslyka=no), «Планируете ли запускать рассылки в будущем? Если да — можем сразу заложить отдельный чекбокс»

## Группа 8. Доступы для разработчика (всегда нужна, формулировка зависит от CMS)

Заголовок группы: «Доступ к сайту»
Контекст: «Без доступа разработчик не сможет внести правки.»

- key: `cms_access`, required, формулировка зависит от CMS (см. adaptation-rules.md):
  - Bitrix: «Можно ли создать пользователя в админке Bitrix с правами на редактирование страниц, шаблонов, веб-форм и `.htaccess`?»
  - Tilda: «Добавите сотрудника в проект Tilda через официальный доступ к проекту?»
  - WordPress: «Создадите пользователя с ролью Administrator?»
  - Иное: «Какой формат доступа удобен — отдельный пользователь, доступ к репозиторию, передача через разработчика клиента?»
- key: `approval_contact`, expected, «Кто с вашей стороны утверждает тексты документов и принимает работы?»

## Формулы для предзаполнения

Если из findings известно:
- контактный email сайта → предложить как ответ для `operator_pd_email` с подтверждением;
- название компании в копирайте footer → предложить как черновик `operator_full_name`;
- адрес «г. Москва» → пометить как недостаточный для `operator_legal_address`, спросить полный;
- найденная Метрика {ID} → подставить в `yandex_metrika_counter`.

## Что НЕ спрашиваем

- Не спрашиваем общие вопросы про «список доменов» — это известно из аудита.
- Не спрашиваем «что продаёт сайт» — это видно с сайта.
- Не спрашиваем «есть ли HTTPS» — это проверяется аудитом.
- Не спрашиваем юридическую квалификацию вопросов — мы не юристы.
