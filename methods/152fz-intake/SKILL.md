# Addu 152-ФЗ — Intake (анкета клиенту)

Второй шаг конвейера. Клиент оплатил работы; нужно собрать у него данные для заполнения политики, согласия, чекбоксов и cookie-баннера. Анкета должна быть точечной, не шаблонной — иначе клиент устаёт и не отвечает.

## Когда использовать

- Клиент согласился на работы и оплатил счёт.
- На руках есть `audit-findings.md`, сгенерированный `addu-152fz-audit` (или принесённый менеджером в любом формате — допустимо).
- Менеджер готов отправить клиенту первое письмо с вопросами.

Не использовать:
- если аудит ещё не сделан — сначала `addu-152fz-audit`;
- если ответы клиента уже получены — переходить к `addu-152fz-generate`.

## Вход

- **Slug клиента** (обязательно) — определяет рабочую папку `documents/{slug}-152fz/`.
- Если в папке нет `audit-findings.md`:
  - спросить у менеджера, где аудит (путь к файлу или вставить текст);
  - если аудита нет совсем — предложить запустить `addu-152fz-audit` сначала.

## Что делает

1. Читает `documents/{slug}-152fz/audit-findings.md`.
2. Анализирует находки и формирует словарь известного и неизвестного:
   - **Известное:** URL сайта, CMS, контакты на сайте, обнаруженные формы и сервисы, severity по каждому пункту.
   - **Неизвестное (надо спросить):** реквизиты оператора, обработчики ПДн, рекламные коммуникации, доступы.
3. Применяет правила адаптации (см. `references/adaptation-rules.md`) — обрезает блоки, которые не нужны для этого сайта:
   - нет корзины в findings → не спрашиваем про платёжные системы и службы доставки;
   - нет регистрации → не спрашиваем про функционал личного кабинета;
   - нет подписки/рассылки → не спрашиваем про сервис email-рассылок (но всё равно спросим, планируются ли рассылки в будущем);
   - Яндекс.Метрика найдена → не спрашиваем «есть ли Метрика», а спрашиваем «подтвердите номер счётчика {ID}»;
   - Метрика не найдена → спрашиваем «не подключается ли Метрика динамически через GTM или модуль CMS».
4. Заполняет заранее то, что видно из findings: «по нашему аудиту, контактный email на сайте — sales@an-pneumatics.ru. Подтвердите, что он же используется для обращений по ПДн, или укажите другой».
5. Формирует два выходных файла (см. ниже).

## Выход

### 1. `documents/{slug}-152fz/client-questionnaire.md`

Готовый текст для отправки клиенту в email или Telegram. Структура:

```
# Сопроводительное письмо (3-4 строки)

Добрый день, {ИМЯ КОНТАКТА}!

Спасибо за оплату работ по 152-ФЗ. Чтобы корректно подготовить документы и внести правки на сайт {URL}, нам нужно уточнить несколько практических деталей. Это не юридическая анкета — мы спрашиваем только то, что не видно с сайта.

Если на какой-то вопрос не знаете ответа — напишите «не знаю», подскажем, как проверить.

---

# Вопросы

(только релевантные блоки, не больше 8-12 вопросов в сумме)
```

Правила формирования:
- максимум 12 вопросов (если больше — скорее всего, что-то можно сгруппировать или перенести в Phase 2 после старта работ);
- группировать по теме, не более 5 групп;
- каждый блок открывается одной фразой контекста («Из аудита мы видим, что у вас есть корзина и регистрация — поэтому нужны такие-то реквизиты»);
- если на сайте уже виден email/телефон/название — предложить их как готовый ответ для подтверждения, а не открытый вопрос;
- избегать вопросов «на всякий случай» — каждый вопрос должен явно влиять на какой-то черновик документа;
- русский язык, тон деловой и тёплый, обращение на «Вы», без юр.жаргона.

### 2. `documents/{slug}-152fz/intake-context.md`

Внутренний файл для `addu-152fz-generate`. Зафиксированный формат:

```markdown
# Intake context — {slug}

Slug: {slug}
URL: {URL сайта}
CMS: {CMS}
Дата intake: {YYYY-MM-DD}

## Что уже известно из аудита

- Контактный email сайта: ...
- Телефон: ...
- Адрес (как указан на сайте): ...
- Видимые формы: ...
- Видимые внешние сервисы: ...
- Корзина / регистрация / личный кабинет: есть/нет
- Cookie-баннер на сайте: есть/нет

## Что мы спрашиваем у клиента в анкете

(список конкретных вопросов в виде ключей, которые ожидаются в answers.md)

- operator_legal_form  → ООО / ИП / самозанятый / физлицо
- operator_full_name   → полное наименование оператора
- operator_inn         → ИНН
- operator_ogrn        → ОГРН/ОГРНИП
- operator_address     → юр.адрес + почтовый адрес для обращений
- operator_pd_email    → email для обращений по ПДн
- hosting_provider     → название хостинг-провайдера
- ...

## Минимально необходимые ответы для старта генерации

Список ключей, без которых `generate` остановится с ошибкой:

- operator_full_name
- operator_inn
- operator_ogrn
- operator_address
- operator_pd_email
- hosting_provider
- has_marketing_rasslyka  (boolean — есть ли рекламные рассылки)

## Дополнительные (желательные, но не блокирующие)

- email_service
- telephony
- crm
- delivery_service
- payment_service
- newsletter_service
- yandex_metrika_counter
- gtm_container
- chat_widget
```

Этот файл — словарь для следующего skill'а. По нему `generate` поймёт, какие ключи искать в answers.md и какие из них обязательны.

## Дополнительный вывод в чат

После создания файлов вернуть менеджеру короткую сводку:

- сколько вопросов в анкете;
- сколько вопросов классифицировано как минимально-необходимые;
- путь к `client-questionnaire.md` (готов к копированию в письмо);
- одна строка: «Когда клиент пришлёт ответы — сохрани их в `documents/{slug}-152fz/answers.md` и запускай `addu-152fz-generate {slug}`».

## Границы

- Не генерировать никаких документов на этом шаге. Никакой политики, согласия, чекбоксов — это работа Skill 3.
- Не запрашивать у клиента то, что уже видно с сайта (телефон, email, домен).
- Не повторять весь шаблон из старого `client-questionnaire.md` — это была проблема первой версии. Только релевантное.
- Не выдумывать, чего нет в findings — если аудит не нашёл корзину, не упоминать корзину в анкете.
